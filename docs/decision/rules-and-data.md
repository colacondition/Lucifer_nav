## 0. 摘要

1. **2027 规则把哨兵从"占点刷伤害"改成"控制区占领 + 控制度消耗战"**：3 个控制区、占领进度 0–5、双方各 600 控制度、
   战亡 −10、差值 200/400 给对方增益（规则 p.37-38）。但**2026 协议（V2.0.0）里没有任何"占领进度 / 控制度"字段**，
   2027 协议又未发布 → **决策重构的第一约束是数据可得性，不是算法**。
2. **哨兵在 2027 被进一步"去人化"**：全自动运行、最多 1 个调试遥控器、五秒倒计时后禁止遥控（p.21、p.57 R22）、
   **多机通信不允许**（p.21）→ 决策必须完全自恢复，且不能指望队友通过裁判系统串口共享状态。
3. **现有 Lucifer 上行裁判帧只带 3 个字段**（`src/serial/include/packet.hpp:41,133-141`，
   `src/serial/doc/referee_frame.md:16-30`），另加 `is_attacked` 由跨帧血量差分派生
   （`src/serial/include/referee_conversion.hpp:33-36,50-51`）。协议里对哨兵决策价值最高的
   **热量/缓冲能量（0x0202）、弹量与金币（0x0208）、增益（0x0204）、RFID（0x0209）、判罚（0x0104）全部未转发**。
4. **2026 协议是"RMUC 优先"的**：0x020B 地面机器人位置只含英雄/工程/3、4 号步兵（p.21），
   0x0305 敌方位置只到选手端（p.34-35），0x0003 只有己方血量（p.10-12）→ **哨兵天然拿不到敌方血量/位置**，
   只能靠视觉（现有 `auto_aim_target_pos`，`src/decision/decision_node/include/decision/target_input.hpp:11-22`）。
5. **V1.9.0 → 2026 V2.0.0 的字段宽度有 9 处不兼容变更**：0x0003(32→20B)、0x0201(13→17B，新增 `bullet_speed_limit`)、
   0x0202(16→14B)、0x0204(7→8B)、0x0208(6→8B)、0x0209(4→5B)、0x020C(1→2B)、0x020D(6→14B)、0x0305(24→48B)，
   0x0120 同长但新增姿态/能量机关位。**沿用 V1.9 解析会静默错位**。
6. **三个最大的数据缺口**（第 4 章矩阵）：① 控制区占领进度与控制度（无字段，只能自估）；② 敌方血量/位置（协议与规则都不给）；
   ③ 复活读条进度（无字段，只能按规则推算 5/10/15…s 或依赖 0x020D 的"可免费复活"位，而后者在 RMUL 2027 是否适用未知）。

## 1. RMUL 2027 规则中与哨兵决策相关的机制

### 1.1 阵容与哨兵身份

- 3V3 阵容：重装（编号 1）、步兵（编号 3）、哨兵（编号 7）；哨兵 **操作手 0 人/台**；每队赛段注册 4 台；
  每场首局最低上场阵容 2 台（表 3-1，p.17）。
- 哨兵"需**全自动运行**，最多配置 1 个遥控器用于调试"（p.21）；**多机通信：不允许**（表 3-5，p.21）。
  多机通信的定义是"机器人间通过裁判系统串口互相通信的交互方式"（表 2-1，p.13）。

### 1.2 哨兵关键特征（表 3-5，p.21-22）

| 项 | 值 | 决策含义 |
| --- | --- | --- |
| 初始/上限血量 | 400 | 单次 17mm 伤害 20（表 3-8，p.30）→ 满血 20 发，容错远高于步兵 350 |
| 底盘功率上限 | 100 W | 高于步兵（75/90W），机动预算更足 |
| 射击热量上限 / 冷却 | 260 / 30 每秒 | 每发 17mm +10 热量（p.31）→ **连续 26 发打满**，冷却 8.7s 回满 |
| 射击初速度上限 | 25 m/s | 超限按表 3-9 锁 15s/20s/当局（p.31） |
| 允许发弹量 | 预装 17mm；**比赛阶段初始 750，局内不可增加**（p.22） | **哨兵不参与兑换经济**，弹药只减不增 |
| 回血 | 激活己方补给区 | 每秒 25% 上限血量（p.36） |
| 复活 | 读条复活 | 见 1.4；**虚弱期必须回补给区解除** |
| 可激活增益点 | 控制区、补给区增益点 | 见 1.7/1.8 |

### 1.3 扣血与超限（决策必须规避的状态）

- 射击热量：每发 +10，**10Hz 结算**冷却（每周期 = 每秒冷却/10）；`Q1>Q0` 时发射机构锁定 + 图传断开，
  直到 `Q1=0`；`Q1>Q2`（17mm：`Q2=Q0+100`）当局锁定且不再解锁（p.31）。
- 底盘功率：缓冲能量上限 60J，10Hz 结算，`Z≤0` 时**底盘断电 5s**（p.33）。
- 异常离线：发射机构、云台、底盘断电，**每秒扣 5% 上限血**、场地交互模块失效、**复活读条不再增加**、多机通信断开（表 3-10，p.34）。
- 装甲/超电离线：每 500ms 扣 `4×N` 血（p.34）；测速模块离线：发射机构立即断电（p.35）。
- 判罚伤害：黄牌扣 15% 上限血、其余存活机器人扣 5%；30s 内再吃黄牌翻倍；3 黄 = 红（p.52-53）。

### 1.4 回血与复活（决策的状态机骨架）

- 回血：重装/步兵/哨兵激活己方补给区，**每秒 25% 上限血量**（p.36）。
- 复活：战亡时热量清零、缓冲能量回满；**自动复活，读条每秒 +1**；首次读条 5，之后每次 **+5**（5/10/15…）；
  复活后血量回到上限的 **20%**、**无敌 30s**、同时进入"虚弱"：**发射机构锁定、无法激活控制区**；
  **检测到己方补给区场地交互模块卡后**虚弱与无敌解除（p.36）。
  → 决策硬约束：**复活后唯一合理目标就是回补给区**（既解除虚弱，又继续回血）。

### 1.5 比赛流程与阶段（0x0001 的 `game_progress` 对应关系）

| 阶段 | 规则页码 | 协议 `game_progress` | 决策要点 |
| --- | --- | --- | --- |
| 准备阶段（3 分钟） | p.48-49 | 1 | 赛场人员调试；结束前 30s 全场上电；**结束后哨兵遥控器放战场入口**（p.49） |
| 十五秒裁判系统自检 | p.50 | 2 | 服务器重置所有机器人血量、检查模块 |
| 五秒倒计时 | p.50 | 3 | **选手端不响应机器人控制指令**（含自定义终端）；倒计时结束后比赛立即开始 |
| 比赛阶段（5 分钟） | p.17、p.39 | 4 | 12m×8m 场地内对抗（p.23） |
| 结算 | p.50 | 5 | 成绩确认 |

- 判罚 **R22**：准备阶段结束后场地人员须把哨兵调试遥控器放战场入口，**五秒倒计时开始后不得使用遥控器调试哨兵**
  （违规：口头警告→红牌→比赛中直接红牌）（p.57）。
- 判罚 **R36**：准备阶段与十五秒自检阶段，战场内机器人**不得离开对应初始区域**（p.58）。

### 1.6 场地元素

战场 12m × 8m（p.23）；模块：补给区、工作台、隧道、高地、红方高地控制区、中央控制区、蓝方高地控制区（图 3-4，p.24）。

- 启动区兼补给区，设工作台，铺场地交互模块卡；**一方补给区相对对方机器人是补给禁区**（p.25-26，图 3-7）。
- 高地：金属板（图 3-8，p.26）；隧道：红/蓝方隧道增益点各一处（图 3-9，p.27）。
- 控制区：位于高地与战场中心，铺场地交互模块卡（3.2.4，p.28，图 3-10/3-11）；**场地交互模块卡可能存在死区**（p.29）。

### 1.7 控制区与控制度机制（2027 新增核心）

- 控制区共 **3 组**：红方高地控制区、蓝方高地控制区、中央控制区；开局均为中立（p.37）。
- 每方对每处控制区有独立"**占领进度**"，范围 **0–5**：计满 5 即"控制"该区，减至 0 即失去控制；
  仅一方激活且对方进度为 0 → 该方 **+1/s**；仅一方激活且对方进度不为 0 → 对方 **−1/s**；
  双方同时激活 → 暂停；双方都不激活且非中立 → 双方各 **−1/s**（p.37）。
- 控制度：开局双方各 **600**；**每控制一处控制区，对方 −1/s**；**每当一方机器人战亡，该方 −10**（p.38）。
- 控制度差 **≥200**：少方复活读条 −33%、补给区回血 33%/s；**≥400**：−50%、50%/s（p.38）。
- 决策含义：**送一台机器人的代价 = 10 控制度 ≈ 单控制区 10 秒的收益**；差值门槛 200/400 会把"占点时间"换算成"对方恢复速度"，
  属于**非线性**激励——需要的是"保住控制区占位"，而不是"多杀"。

### 1.8 场地增益

- 高地增益点兼高地控制区：激活即得 **25% 防御增益**；双方机器人均可激活（p.38）。
- 隧道增益点：**同一台机器人在 3 秒内检测到一方场地两处隧道增益点的场地交互模块卡、且途中没有检测到其他场地交互模块卡**
  → 获得 **1.5 倍热量冷却增益，持续 60s**（p.38）。*注：规则文字说"两处"、图 3-9（p.27）每方仅标 1 处，存在歧义，需官方答疑确认。*
- 增益失效：机器人**未检测到**增益点卡后，激活状态 **2 秒后失效**（p.38）。

### 1.9 经济与兑换（哨兵基本无关，但要读懂"对方"）

- 金币增量（表 3-11，p.36）：开局 200；`03:59` +200；`02:59` +200；`01:59` +300；`00:59` +300。
- 控制度差首次达 **200/400** 时，控制度较少方 +200 金币，每局最多 400（p.36）。
- 兑换比例（表 3-12，p.37）：17mm **10 金币/10 发**；42mm 10 金币/1 发；**仅重装、步兵**在激活补给区时可由操作手兑换（p.37）。
- **哨兵 750 发局内不可增加**（p.22）→ 决策不需要考虑"哨兵买弹"，但要考虑**对方的弹量曲线**（对方步兵可买弹）。

### 1.10 胜负条件（p.39）

1. 一方控制度为 0 → 当局立即结束，另一方胜；2. 时间耗尽且控制度不同 → 高者胜；
3. 控制度相同 → 全队攻击伤害高者胜；4. 仍相同 → 全队总剩余血量高者胜；5. 仍无法判定 → 平局（淘汰赛加赛）。
赛制：小组循环 BO2、淘汰赛 BO3（p.39）。

### 1.12 规则对决策架构的硬含义

1. **无人工兜底**：全自动 + 禁遥控（p.21、R22 p.57）→ 任何"等人来救"的状态机分支都是死路。
2. **不能靠队友数据**：多机通信不允许（p.21）→ 队内协同只能靠"共享的先验/时间表"（如统一的开局路线），不能靠实时消息。
3. **死亡代价指数化**：−10 控制度（p.38）+ 读条 5/10/15…递增（p.36）→ 第 2、3 次死亡几乎等于让出控制区。
4. **复活后唯一目标**：回补给区解除虚弱（p.36）——这是状态机里最硬的边。
5. **占点优先于击杀**：控制度按"控制区数量"每秒流失（p.38），胜负第 1 条是控制度归零（p.39）。
6. **两处增益都要求"卡序"**：隧道要求 3s 内两处卡且途中无其它卡（p.38）→ 路径规划要"卡感知"，不是纯几何最短。

## 2. 2026 通信协议 V2.0.0：哨兵能收到什么、能发什么

### 2.1 链路与时延

- 常规链路：电源管理模块 User 串口，**115200**；图传链路 921600；8 数据位、1 停止位、无校验（表 1-1/1-2，p.5）。
- 帧格式未变：`frame_header(5) + cmd_id(2) + data(n) + frame_tail(2, CRC16)`；SOF=0xA5（表 1-2/1-3/1-4，p.5）。
- 时延：正常 **约 130ms、丢包 <1%**；网络恶劣 **约 200ms、丢包约 3%**；"测量数据可能存在误差，数据仅供参考"（p.6）。
  → 任何"按帧做闭环"的策略都要按 **200ms 延迟**设计。
- 适用范围：RMUC 与 RMUL 共用条目适用；**仅适用某一赛项的条目默认不适用另一赛项**（前言，p.3）——这是 2027 不确定性的根源。

> 结论：**任何"照抄 V1.9 结构体"的解析都会静默错位**（尤其 0x0201 的 4 字节 float 插入）。
> 现有 Lucifer 并不直接解析协议，而是由电控转发自定义帧（`src/serial/include/packet.hpp:117-141`），
> 因此**协议版本风险目前被隔离在电控侧**——这是重构时要保留的边界。

### 4.3 "无法获得"项的替代方案

| 缺口 | 替代 | 精度/风险 |
| --- | --- | --- |
| 控制区占领进度 | 自估：0x0209 的"己方/对方控制区 RFID" + 0x0101 中心增益点占领位 + 计时积分（规则 p.37 每秒 ±1） | 依赖 RFID 死区（p.29）、0x0209 的 3Hz 采样与增益点 2s 失效（p.38）；**会漂移**，只能做"事件驱动"不能做数值最优 |

## 5. 对决策重构的接口建议（只读结论，未改代码）

1. **继续让电控做唯一协议解析方**：NUC 不直连主控 User 串口（会与电控争用 115200 链路，且协议版本风险会扩散到 NUC）。
   电控只做"搬运 + 缓存保活"，不做业务判断——这与现有两条硬要求一致（`src/serial/doc/referee_frame.md:42-52`）。
2. **`'H','R'` 帧尾部追加，保持 `payload_len` 机制**（`src/serial/include/packet.hpp:29-40,133-141` 已为此设计）。
   建议追加顺序（按决策价值/字节成本）：
   `hp_max(2) → heat(2) → heat_limit(2) → cooling(2) → buffer_energy(2) → ammo17(2) → gold(2) →
   buffs(4: recovery/cooling/defence/attack) → rfid(5) → warning(3) → damage_diff(2) → self_pos(12)`。
   一次性规划好偏移，避免多轮追加导致电控固件反复改版。
3. **数据分级**：硬实时（血/热量/缓冲/弹量，10Hz）、软实时（增益/RFID，3Hz）、慢变量（判罚 1Hz、位置 1Hz）。
   决策里"慢变量"不得进高频闭环（协议本身 130–200ms 延迟，p.6）。
4. **不确定项的隔离**：把 U1–U10 全部集中在 `referee_conversion`（或新的 `referee_schema`）一层的"版本适配器"里，
   决策层只消费稳定的语义字段；2027 协议发布后只改适配器。
5. **自估模块独立**：控制度/占领进度估计器作为独立节点（输入：RFID、血量、时间；输出：估计值与置信度），
   决策按"置信度低就退回事件驱动策略"使用——不要把估算值当硬事实。
6. **BT 迁移**：`ros2行为树.pdf` 的目录结构（20 章）已覆盖重构所需全部机制：异步动作（p.21）、回退/序列/并行（p.30-42）、
   条件与 Switch（p.42）、装饰节点（p.44）、子树模块化（p.49）、**脚本与前后置条件**（p.65）、
   **全局黑板与数据架构**（p.74）、模拟测试与节点替换（p.78）、日志（p.82）、Groot2（p.86）、ROS2 集成（p.99）。
   建议把"控制度/占领进度估计"放黑板、把"复活/回家"做成子树，正好对应 1.12 的硬约束。
